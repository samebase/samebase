# Client ID Metadata Documents: the reader

`@samebase/identity-broker/cimd` reads and checks an OAuth Client ID Metadata Document, as
[draft-ietf-oauth-client-id-metadata-document-03](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-03.html)
defines it. It has the rules of the draft that need no policy of a server. It knows nothing of the
broker: no store, no client card, no layer. Its only dependency is `effect`.

| Function                   | What it does                                                                                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `parseClientId(raw)`       | The rules of section 3 on the raw text. A `ClientId` (the raw text as the identity, the host and origin, `hasQuery`, `hasExplicitPort`) or a refusal.                    |
| `fetchDocument(id, fetch)` | One GET (an Effect). A `Document` (the JSON object and `freshUntil`), a `Transient` failure (no answer, time-out, 429, 5xx, with `retryAfter`), or a `Terminal` failure. |
| `checkDocument(id, json)`  | The rules of sections 4 to 6. A `Checked` record or a refusal.                                                                                                           |
| `freshness(headers, now)`  | Until when an answer is fresh (epoch milliseconds), from `Cache-Control` and `Age`.                                                                                      |
| `refusals`                 | One sentence for each fixed code (`RefusalCode`). No text holds content of the document.                                                                                 |

## Usage

```ts
import { Effect } from "effect";
import {
  checkDocument,
  fetchDocument,
  parseClientId,
  refusals,
} from "@samebase/identity-broker/cimd";

const resolve = Effect.fn(function* (raw: string) {
  const clientId = parseClientId(raw);
  if (clientId._tag === "Refused") {
    return { error: "invalid_client", description: refusals[clientId.code] };
  }
  // On Workers and Node the platform fetch keeps the request's `redirect: "manual"`. On a platform
  // that follows redirects anyway (Convex), give a function that does not.
  const fetched = yield* fetchDocument(clientId, fetch);
  if (fetched._tag === "Transient") {
    return { status: 503, retryAfter: fetched.retryAfter };
  }
  if (fetched._tag === "Terminal") {
    return { error: "invalid_client", description: refusals[fetched.code] };
  }
  const checked = checkDocument(clientId.id, fetched.json);
  if (checked._tag === "Refused") {
    return { error: "invalid_client", description: refusals[checked.code] };
  }
  // Policy: take the parts of the record that this server supports.
  return {
    authMethod: checked.authMethods.includes("none") ? "none" : undefined,
    redirectUris: checked.redirectUris.filter((r) => r.kind === "https").map((r) => r.uri),
    grantTypes: checked.grantTypes.filter((g) => g === "authorization_code"),
    responseTypes: checked.responseTypes.filter((r) => r === "code"),
    freshUntil: fetched.freshUntil,
  };
});
```

The record reports all that the document declares: every authentication method, the keys or the key
address, every grant and response type, and every redirect URI as written with its kind (`https` on
a DNS name, `loopback`, or `other`). A server takes the part that it supports and refuses only when
nothing usable is left (draft section 5, and the faults that other servers had with the documents of
ChatGPT, VS Code and Claude).

## Choices of the reader

- **The id is fetched as named.** Draft section 3 forbids normalization in comparison, and section 4
  requires that the fetched URL match the id. The URL parser of fetch rewrites some texts (an IPv4
  shorthand, a percent-encoded host, `'` in a query, an empty port). So `parseClientId` refuses a
  text that the parser would change, except for what gives the same request: the case of the scheme
  and the host, and an explicit port 443. Those stay in the identity, so `https://example.com:443/c`
  and `https://example.com/c` are two clients, as section 3 says.
- **Only RFC 3986 URIs.** A text with a space, a backslash or a character outside ASCII is refused:
  it is not a URI, and the URL parser would repair it.
- **A literal special-use address is never fetched.** Section 10.7 forbids a fetch to a special-use
  address. The reader refuses a host that is one by itself: an IP address of the IANA
  special-purpose registries (RFC 6890) or multicast, and `localhost` with its subdomains (RFC
  6761). What a DNS name resolves to is not visible to the reader: that is the platform's part.
- **A `software_statement` is refused.** The reader does not validate one, and section 4.1 puts the
  same restrictions on its contents.
- **Members with a wrong type are refused** (`invalid_member`, with the member's name), for the
  members that the record reports. Other members are ignored.

## Requirements of draft -03 for an authorization server

Each MUST, MUST NOT, SHOULD and SHOULD NOT of the draft that applies to an authorization server.
"Reader" names the function and the test in `src/cimd/reader.test.ts` (by the start of its title).
"Server" is a part that needs a server's policy, state or endpoint. "Not supported" says why.

and stable id is RECOMMENDED), section 4.5 (the document MUST NOT come from untrusted input),
section 5 (a client SHOULD use the plural member; the singular one is NOT RECOMMENDED; a client that
can keep a private key SHOULD use it), and Appendix A (a CIMD Service MUST return valid documents).

## Not in the record

The record has the members that a server needs to decide: the id, the redirect URIs, the
authentication methods, the keys, the grant and response types, and `client_name`, `client_uri`,
`logo_uri`, `policy_uri` and `tos_uri` as asserted by the client (section 10.10). It does not have
`scope`, `contacts`, `software_id`, `software_version`, the members of RP Metadata Choices other
than the authentication methods, or the language variants of RFC 7591 section 2.2
(`client_name#ja`). A server that needs one reads it from the `json` of the `Document` result.

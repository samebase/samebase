# Client ID Metadata Documents: the reader

`@samebase/identity-broker/cimd` reads and checks an OAuth Client ID Metadata Document (CIMD), as
[draft-ietf-oauth-client-id-metadata-document-03](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-03.html)
defines it. It has the rules of the draft that need no policy of a server. It knows nothing of the
broker: no store, no client card, no layer. Its only dependency is `effect`.

| Function                   | What it does                                                                                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `parseClientId(raw)`       | The rules of section 3 on the raw text. A `ClientId` (the raw text as the identity, the hostname and origin, `hasQuery`, `hasExplicitPort`) or a refusal.                |
| `fetchDocument(id, fetch)` | One GET (an Effect). A `Document` (the JSON object and `freshUntil`), a `Transient` failure (no answer, time-out, 429, 5xx, with `retryAfter`), or a `Terminal` failure. |
| `checkDocument(id, json)`  | The rules of sections 4 to 6. A `Checked` record or a refusal.                                                                                                           |
| `freshUntil(headers, now)` | Until when an answer is fresh (epoch milliseconds), from `Cache-Control` and `Age`.                                                                                      |
| `refusalDescriptions`      | One sentence for each fixed code (`RefusalCode`). No text holds content of the document.                                                                                 |

## Usage

```ts
import { Effect } from "effect";
import {
  checkDocument,
  fetchDocument,
  parseClientId,
  refusalDescriptions,
} from "@samebase/identity-broker/cimd";

const resolve = Effect.fn(function* (raw: string) {
  const clientId = parseClientId(raw);
  if (clientId._tag === "Refused") {
    return { error: "invalid_client", description: refusalDescriptions[clientId.code] };
  }
  // On Workers and Node the platform fetch keeps the request's `redirect: "manual"`. On a platform
  // that follows redirects anyway (Convex), give a function that does not.
  const fetched = yield* fetchDocument(clientId, fetch);
  if (fetched._tag === "Transient") {
    return { status: 503, retryAfter: fetched.retryAfter };
  }
  if (fetched._tag === "Terminal") {
    return { error: "invalid_client", description: refusalDescriptions[fetched.code] };
  }
  const checked = checkDocument(clientId.id, fetched.json);
  if (checked._tag === "Refused") {
    return { error: "invalid_client", description: refusalDescriptions[checked.code] };
  }
  // Policy: take the parts of the record that this server supports.
  return {
    authMethod: checked.authMethods.includes("none") ? "none" : undefined,
    redirectUris: checked.redirectUris.filter((r) => r.kind === "https").map((r) => r.uri),
    grantTypes: checked.grantTypes.filter((g) => g === "authorization_code"),
    responseTypes: checked.responseTypes.filter((r) => r === "code"),
    freshUntil: fetched.freshUntil,
  };
});
```

The record reports all that the document declares: every authentication method, the keys or the key
address, every grant and response type, and every redirect URI as written with its kind (`https` on
a DNS name, `loopback`, or `other`). A server takes the part that it supports and refuses only when
nothing usable is left (draft section 5, and the faults that other servers had with the documents of
ChatGPT, VS Code and Claude).

## Choices of the reader

- **The id is fetched as named.** Draft section 3 forbids normalization in comparison, and section 4
  requires that the fetched URL match the id. The URL parser of fetch rewrites some texts (an IPv4
  shorthand, a percent-encoded host, `'` in a query, an empty port). So `parseClientId` refuses a
  text that the parser would change, except for what gives the same request: the case of the scheme
  and the host, and an explicit port 443. Those stay in the identity, so `https://example.com:443/c`
  and `https://example.com/c` are two clients, as section 3 says.
- **Only RFC 3986 URIs.** A text with a space, a backslash or a character outside ASCII is refused:
  it is not a URI, and the URL parser would repair it.
- **A literal special-use address is never fetched.** Section 10.7 forbids a fetch to a special-use
  address. The reader refuses a host that is one by itself: an IP address of the IANA
  special-purpose registries (RFC 6890) or multicast, and `localhost` with its subdomains (RFC
  6761). What a DNS name resolves to is not visible to the reader: that is the platform's part.
- **A `software_statement` is refused.** The reader does not validate one, and section 4.1 puts the
  same restrictions on its contents.
- **Members with a wrong type are refused** (`invalid_member`, with the member's name), for the
  members that the record reports. Other members are ignored.

## Requirements of draft -03 for an authorization server

Each MUST, MUST NOT, SHOULD and SHOULD NOT of the draft that applies to an authorization server.
"Reader" names the function and the test in `src/cimd/reader.test.ts` (by the start of its title).
"Server" is a part that needs a server's policy, state or endpoint. "Not supported" says why.

## The server's part in this broker

Where `@samebase/identity-broker` does each "Server" row of the table above. "Layer" is the CIMD
layer, `Registration.clientIdMetadataDocuments` (`src/layers/cimd/`); "core" is the sign-in code
(`src/core/`, `src/rules/`).

| Section | Requirement                                                   | In this broker                                                                                                                                                                                                                                                                                           |
| ------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3       | SHOULD NOT contain a query (refusal is policy)                | Layer: an id with a query is refused (`client_id_query`), and so is one with a port, one over 255 characters, and one whose host is not a DNS name.                                                                                                                                                      |
| 3       | Stored ids compared by simple string comparison               | Core: `/authorize` does not trim an `https://` id, and every step reads the card by the exact id. An id that starts with `HTTPS://` (the scheme has no case in RFC 3986, so `parseClientId` accepts it) is not an id of the layer: the broker answers that the client is unknown.                        |
| 4.2     | Redirect URIs registered, matched by simple string comparison | Core: `/authorize` and `/token` compare the address with the card's list as strings. Layer: the card holds the https addresses of the document on the id's origin. The loopback port rule: not done, the layer ignores loopback addresses (a laptop client needs the port rule of RFC 8252 in the core). |
| 5       | SHOULD select one supported value                             | Layer: it selects `none` and ignores the other methods and the keys.                                                                                                                                                                                                                                     |
| 5       | A `none` client that sends authentication: `invalid_client`   | Core: the token endpoint refuses a secret or a client assertion for a public card.                                                                                                                                                                                                                       |
| 5       | No supported method: `invalid_client`                         | Layer: a document without `none` is refused (`no_none_method`); the broker's page names `invalid_client`. With no card, `/token` answers `invalid_client`.                                                                                                                                               |
| 5       | SHOULD advertise its methods                                  | Core: discovery adds `none` to `token_endpoint_auth_methods_supported` when a layer resolves ids.                                                                                                                                                                                                        |
| 5       | A JWT method needs `jwks` or `jwks_uri`                       | Not done: the layer never selects a key method.                                                                                                                                                                                                                                                          |
| 6       | MUST intersect `grant_types` and `response_types`             | Layer: `authorization_code` and `code` must be present (`no_code_grant`, `no_code_response`).                                                                                                                                                                                                            |
| 6       | SHOULD re-fetch periodically                                  | Layer: the first sign-in after `freshUntil` reads the document again, and so does a sign-in whose return address is not on the fresh card but is https on the id's origin. There is no background refresh: a card that nobody uses is not read.                                                          |
| 6.1     | SHOULD abort the authorization request when the fetch fails   | Layer: a transient failure answers 503 with `Retry-After`; a terminal one answers 400 and deletes the card.                                                                                                                                                                                              |
| 6.1     | A transient failure keeps trust and the cached document       | Layer: the card stays. It gives no new sign-in after `freshUntil`; a sign-in in progress goes on. The broker issues no refresh token to a sign-in client.                                                                                                                                                |
| 6.1     | A `client_id` mismatch SHOULD invalidate refresh tokens       | Layer: the card is deleted. No refresh token exists to invalidate.                                                                                                                                                                                                                                       |
| 6.1     | MUST NOT redirect to the client on a failure                  | Core: a refusal of the layer is the broker's own error page.                                                                                                                                                                                                                                             |
| 6.1     | At the token or PAR endpoint: `invalid_client` or 503         | Core: `/token` never fetches; it reads the stored card, and with no card answers `invalid_client`. The broker has no PAR endpoint.                                                                                                                                                                       |
| 6.2     | MUST NOT cache errors or invalid documents                    | Layer: only a document that `checkDocument` and the policy accept is stored.                                                                                                                                                                                                                             |
| 7       | The authorization response includes `iss`                     | Core: every redirect to the client carries `iss`.                                                                                                                                                                                                                                                        |
| 8       | Discovery includes `client_id_metadata_document_supported`    | Core: present when a mounted layer resolves ids.                                                                                                                                                                                                                                                         |
| 9.1     | Generated ids do not start with `https://`                    | Layers: the GitHub and stack layers make `cl_` ids.                                                                                                                                                                                                                                                      |
| 9.2     | SHOULD fetch the document when it pre-registers an id         | Not done: the broker pre-registers no `https://` id.                                                                                                                                                                                                                                                     |
| 10.1    | SHOULD refuse its own issuer or a party it trusts             | Layer: an id on the broker's own origin is refused (`broker_origin`). A list of trusted parties: not done, the broker has none; `hosts` limits the layer to named hosts.                                                                                                                                 |
| 10.6    | SHOULD show the host of the id                                | Core: every card of the layer has `confirm: true`, so the default page shows the host of the return address, which the layer requires on the id's origin. | 10.7    | What a DNS name resolves to is never a special-use address    | The host's runtime: Cloudflare Workers and the default Convex runtime refuse private addresses. | 10.7    | OWASP SSRF recommendations, network policies                  | The host's runtime, and the layer's fetch budget for the whole broker (default 120 each minute).                                                                                                                                                                                                         |
| 10.7    | Only known schemes for display members                        | Layer: it shows no display member.                                                                                                                                                                                                                                                                       |
| 10.12   | A persisted decision is scoped to the id and the resource     | Not applicable: the broker keeps no consent decision. The page is shown at each sign-in.                                                                                                                                                                                                                 |

## Not in the record

The record has the members that a server needs to decide: the id, the redirect URIs, the
authentication methods, the keys, the grant and response types, and `client_name`, `client_uri`,
`logo_uri`, `policy_uri` and `tos_uri` as asserted by the client (section 10.10). It does not have
`scope`, `contacts`, `software_id`, `software_version`, the members of RP Metadata Choices other
than the authentication methods, or the language variants of RFC 7591 section 2.2
(`client_name#ja`). A server that needs one reads it from the `json` of the `Document` result.

# Samebase Organization Context And Routes

This plan turns the accepted GitHub-backed organization model into one product model. Review the
canvas first. It shows the global inventory, an organization page, the small-screen context, and the
switch menu.

## Outcome

<Callout id="organization-context-decision" tone="decision">

Use `/org/<github-owner>` for organization-owned pages, keep `/vault/<owner>/<repo>` for vaults,
group `/vault` by organization, and do not save an active organization.

</Callout>

Done means that a user can always answer three questions from the route and header: which Samebase
account is signed in, which organization owns the current work, and which vault is open.

## Scope

- Create one organization route family for vaults, providers, app creation, repository connection,
  billing, and future member administration.
- Put the organization context in shared main-pane chrome.
- Keep one user-global vault inventory with visible organization sections.
- Split user settings from organization administration.
- Delete personal vault folders and their stored data after approval.
- Add explicit zero-membership and lost-membership states.

This plan does not change organization ownership, Samebase login, GitHub admission, the FileView
editor, or provider resource ownership. It does not add an enterprise account layer.

The route owner is authoritative. The application resolves it to an internal organization ID only
after it checks current Samebase membership. A missing membership renders an unavailable state on
the same URL. `/org/:owner` redirects to its vault list only after this check succeeds.

## Interaction Rules

1. The main-pane header shows `All vaults`, `Account`, or the GitHub owner login.
2. A one-organization user sees a static owner label without a chevron.
3. A multi-organization user gets a switch menu in that same place.
4. Switching from an organization page keeps the same section when possible.
5. Switching from a vault goes to the target organization's vault list.
6. Every switch creates a normal history entry. Back restores the prior owner.
7. The global `/vault` page has no active organization.
8. The right navigation uses links for the owner in the route.
9. The global `/vault` page always offers `Install GitHub App` so any user can add another owner.

## Settings Boundary

User settings contain the display name, user preferences, sign-out, account deletion, MCP clients,
and personal GitHub user authorization. Organization administration contains GitHub App installation
health, providers, billing, members, roles, and later organization-level destructive actions.

MCP consent stays user-global. Each MCP operation checks current membership for the target resource.

## Folder Reduction

The current folder tables are user-owned and can place vaults from several organizations under one
personal heading. Remove that hierarchy. Derive organization sections from memberships and vault
ownership. Delete the stored assignments and folders because a mixed folder has no safe organization
target.

## Delivery Slices

### 1. Organization routes and shared context

Add the route namespace and shared resolver. Move providers, app creation, repository connection,
GitHub installation health, and billing. Add the main-pane organization control. Make the right
navigation owner-aware. Move MCP clients and personal GitHub user authorization to user settings.
Return provider OAuth and billing flows to their scoped organization routes. Delete unscoped page
selectors. After approval, update organization ownership Spec 120.

### 2. Vault separation and folder deletion

Group `/vault` by organization. Limit the vault detail picker to one organization. Delete folder
tables, APIs, UI, tests, and cleanup paths. Add desktop and mobile screenshot coverage.

### 3. Access-state acceptance

Add the no-organization, unavailable organization, and unavailable vault states. Test zero, one,
several, and removed memberships. Test reload, direct links, Back, Forward, mobile panes, roles, and
MCP target checks. Test full-page provider OAuth and billing returns, including membership removal
during the external flow. Confirm that signed-out deep links return to the same route after sign-in.

## Risks

<Callout id="organization-context-risks" tone="risk">

The main correctness risk is silent fallback to a different organization. The route resolver and
every scoped page must fail closed for the owner in the URL. GitHub owner rename handling remains a
separate identity synchronization task.

</Callout>

## Verification

1. Run `pnpm dev --once` in the implementation worktree before tests.
2. Run `pnpm check` and the focused route, organization, billing, provider, folder-removal, and MCP
   tests.
3. Run `pnpm test:visual:linux` for canonical desktop and mobile visual acceptance.
4. In the real app, test zero, one, several, and removed memberships.
5. For each state, test direct links, reload, Back, Forward, organization switching, provider
   actions, billing, and vault detail navigation.
6. Inspect every rendered URL and link. Confirm that no internal organization ID is present.

## Summary

`WorkspaceLayoutV2` is the canonical Samebase layout primitive. The long-term vision is that it
becomes an open-source package and the only layout primitive that Samebase routes rely on.

Public routes, legal routes, fast landing paths, static fallbacks, and future prerendered documents
must not maintain a second hand-written approximation of that layout. If a route needs the Samebase
shell, it must render through `WorkspaceLayoutV2` itself. If a build-time prerender cannot use the
canonical component tree, that prerender path is incomplete and should be replaced rather than
expanded.

## Vision

- `WorkspaceLayoutV2` is package-shaped product infrastructure, not a local convenience wrapper.
- Samebase should have one layout contract for app, public, legal, and workspace surfaces.
- Route shells should consume `WorkspaceLayoutV2` directly through shared layout boundaries such as
  `Layout.tsx` and public/workspace route layouts.
- Static and prerendered output should be generated by rendering the canonical React component tree,
  not by copying class strings from it.
- Compatibility with older bespoke public shells is a non-goal for app-owned code.

## Non-Goals

- Keeping a second public/legal layout around because it is "close enough."
- Maintaining string-built copies of `WorkspaceLayoutV2`, pane frames, rails, status bars, or route
  chrome.
- Adding pass-through props, mirrors, adapters, or fallback wrappers to preserve behavior from
  temporary static-route workarounds.
- Treating hydration mismatch cleanup as a reason to duplicate the layout in build scripts.

## Accepted Contract

### One Layout Primitive

Any route that needs Samebase chrome must use `WorkspaceLayoutV2` through the shared app route tree.
This includes public routes such as `/`, `/terms`, and `/privacy`.

The route may choose which panes exist and what content they contain, but the pane geometry, resize
behavior, mobile carousel behavior, headers, footers, and scroll ownership must come from
`WorkspaceLayoutV2`.

### Prerendering

Prerendering must be implemented with a standard React render path that invokes the same components
used by the hydrated route. Acceptable approaches include a dedicated build-time React render entry
or a route-level prerender pipeline that renders the shared route tree.

The prerender must not:

- concatenate a parallel copy of `WorkspaceLayoutV2` HTML
- copy Tailwind class strings out of the layout components
- rebuild `SidebarProvider`, pane frames, status bars, or public rails by hand
- preserve an older static shell because it avoids importing the real layout

If importing the real component tree makes the public startup bundle too large, the fix belongs in
the canonical components and their dependency boundaries, not in a separate shell.

### Static Route HTML

String-built public route shell code must not be kept as a transitional workaround. It can stamp
metadata on an existing app document, but it must not inject route layout or route chrome.

Only add public/legal route prerendering when it renders the same
`Layout -> PublicLayoutShell -> WorkspaceLayoutV2` tree used at runtime.

### Performance

`WorkspaceLayoutV2` should stay small enough to use everywhere. When the public landing page becomes
heavy, the first question is which dependency crossed into the canonical layout path. Remove or
lazy-load that dependency at the source.

Do not solve public performance regressions by inventing a lighter parallel layout.

### Validation

Public route validation should assert:

- direct `/terms` and `/privacy` loads render through the same route tree as client navigation
- landing reloads do not jump between initial render and settled layout
- production `/` does not preload editor, WebGL, analytics, private workspace, or route-not-found
  chunks before they are needed
- no test depends on markers from a removed static legal shell

## Operator Reminder

When future work touches public routes or prerendering, start from this rule: `WorkspaceLayoutV2` is
the product layout. Do not mirror it. Use it, make it smaller, or delete the competing path.
